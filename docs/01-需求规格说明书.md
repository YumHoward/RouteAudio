## 1. 背景与问题

### 1.1 用户之痛

现代 Windows 用户在**同一台机器上同时运行多个发声程序**是常态：游戏、音乐、语音通话、直播推流、浏览器视频、系统提示音。而 Windows 的音频输出模型是**端点级**的：

```
应用 → 音频会话（Session）→ 音频引擎（Audio Engine）→ 端点（Endpoint）→ 驱动 → 物理设备
```

同一个时刻只有一个「默认播放设备」，所有没有单独指定端点的程序都往它送声音。用户想做到的这些事，原生体验都很差：

| 用户诉求 | 原生现状 | 痛点 |
| --- | --- | --- |
| 游戏声走耳机、音乐走音箱 | Win10 1803+ 的「应用音量和设备首选项」、Win11 的「音量合成器」可以逐应用选设备 | 只能对**当前正在出声**的应用操作；程序没出声就找不到；换设备后要重来；没有规则、没有配置档 |
| 直播时游戏声进耳机、观众听到混音 | 需借助 VoiceMeeter 等虚拟调音台 | 学习成本极高，概念多（虚拟输入/输出、A1/A2/B1） |
| 会议软件走通讯耳机，其余走音箱 | 需反复切换默认设备 + 通讯设备 | 通话音量和媒体音量互相打架 |
| 换场景（游戏 ↔ 工作）批量切换 | 逐项手改 | 5 个程序 × 3 个设备 = 15 次点击 |
| 某个程序总是跑到错的设备 | 每次手动 | 程序重启后策略丢失或未生效 |

### 1.2 现有方案对比

| 方案 | 按应用路由 | 自动化 | 延迟/音质 | 成本 | 主要缺点 |
| --- | --- | --- | --- | --- | --- |
| Windows 设置（应用音量/音量合成器） | ✅ | ❌ | 无影响 | 免费 | 无规则、无配置档、入口深、不显示未发声应用 |
| EarTrumpet（开源） | ✅（较新版本） | ❌ | 无影响 | 免费 | 定位是音量混合器，非路由工具；无持久规则 |
| Audio Router（开源，已停止维护） | ✅ | ❌ | 无影响 | 免费 | 2016 年后停更，Win11 兼容性差 |
| VoiceMeeter / VB-Audio Matrix | ✅（通过虚拟设备） | 部分 | 有额外缓冲 | 捐赠/付费 | 概念复杂，需重装驱动，多设备时钟问题 |
| CheVolume / 商业路由工具 | ✅ | 部分 | 有驱动/钩子 | 付费 | 闭源，历史上有兼容性与稳定性问题 |
| SoundSwitch | ❌（只切默认设备） | ✅ | 无影响 | 免费 | 不解决「同时多设备」 |
| 本项目 | ✅ | ✅ | 无影响（A 路线） | 免费/MIT | 依赖系统内部 API，需跟随 Windows 版本维护 |

**结论**：不是从零解决「能不能路由」，而是解决**「能不能稳定、自动、可切换地路由」**。差异化 = 规则引擎 + 配置档 + 热插拔自愈 + 可观测 + 脚本化。

### 1.3 立项判断

- 技术可行：系统内部 API 已被 EarTrumpet / SoundSwitch 等成熟项目长期使用，Win10 1803 → Win11 均可用；进程级回环采集自 Win10 2004 起为公开 API。
- 时机合适：Win11 用户对「多设备 + 多场景」的需求随远程办公、直播、掌机/客厅 PC 普及而增长。
- 风险可控：主路线不碰内核、不装驱动、不需管理员权限，失败模式是「路由不生效」，而不是「系统蓝屏/爆音」。

## 2. 目标与非目标

### 2.1 产品目标（可度量）

| 编号 | 目标 | 度量 |
| --- | --- | --- |
| G-1 | 让「游戏走 A、音乐走 B」在 60 秒内完成配置 | 新用户从安装到完成首次双设备路由 ≤ 60 s（可用性测试，5 名用户中 4 名达成） |
| G-2 | 路由在一次配置后长期稳定生效 | 连续 7 天日常使用中，无需人工干预的路由成功率 ≥ 99%（按每次程序启动计） |
| G-3 | 不劣化音质、不引入可感知延迟 | A 路线：0 额外延迟、位精确；B 路线：端到端 P95 ≤ 50 ms、24 h 内爆音 0 次 |
| G-4 | 场景切换足够快 | 配置档切换（≤ 10 个应用）≤ 1.5 s 完成 |
| G-5 | 足够轻 | 空闲 CPU ≤ 0.3%，常驻内存 ≤ 120 MB |

### 2.2 非目标（明确不做）

- 不做「音频后期处理」：不做 EQ、压缩、降噪、变声（v2 再评估 EQ）。
- 不做网络音频传输（类似 AudioRelay / SoniqCast）。
- 不做专业音频：不提供 ASIO、不追求 < 10 ms 延迟。
- 不做「同一程序的不同窗口/不同声音分流」——Windows 的会话粒度是进程，做不到。
- 不做 DRM 绕过、不做反作弊对抗、不注入进程。

## 3. 术语表

| 术语 | 说明 |
| --- | --- |
| 端点（Endpoint） | 一个可选的音频输出设备实例，如「扬声器 (Realtek Audio)」。ID 形如 `{0.0.0.00000000}.{guid}` |
| 设备角色（Role） | 每个端点有三个角色：`eConsole`（控制台/默认）、`eMultimedia`（多媒体）、`eCommunications`（通信）。系统分别维护三个「默认设备」 |
| 音频会话（Session） | 一个进程在某端点上的一组音频流的容器。音量/静音的作用域 |
| 策略路由（Policy Routing） | 通过系统内部 API 把「某进程默认使用哪个端点」写入系统策略，由音频引擎执行 |
| 进程回环（Process Loopback） | 采集指定进程（树）正在渲染的音频，而不经过物理设备 |
| 配置档（Profile） | 一组「应用 → 设备」映射 + 音量设置，可整体切换 |
| 路由计划（Route Plan） | 根据配置档 + 规则 + 当前状态计算出的、待执行的期望状态集合 |
| 兜底（Fallback） | 设备消失或路由失败时的降级行为 |

## 4. 用户与场景

### 4.1 用户画像

| 画像 | 特征 | 核心诉求 | 占比预估 |
| --- | --- | --- | --- |
| **双设备玩家** | 游戏耳机 + 桌面音箱 / 显示器音箱；常开语音 | 游戏进耳机、音乐与语音分离 | 45% |
| **直播/内容创作者** | OBS、采集卡、监听耳机、多路混音 | 观众听混音、自己听监听、游戏声不能重复 | 20% |
| **远程办公者** | 会议耳机 + 音箱；Teams/Zoom/飞书 | 会议强制进耳机，媒体走音箱 | 20% |
| **客厅/HTPC 用户** | 电视 HDMI + 功放 + 蓝牙耳机 | 影音走功放，游戏走耳机，一键切换 | 10% |
| **折腾型开发者** | 多声卡、虚拟设备、脚本化 | CLI/API、配置可版本化 | 5% |

### 4.2 场景故事

**场景 A：双设备玩家（核心场景）**

> 小张有 USB 游戏耳机和一对桌面音箱。他一边打《赛博朋克》一边用 Spotify 放歌。他打开 RouteAudio，把 `Cyberpunk2077.exe` 拖到「耳机」，把 `Spotify.exe` 拖到「音箱」，勾选「记住」。之后每次开机、每次游戏启动，路由自动生效。朋友 Discord 语音进来时，Discord 自动落在「通信」角色设备（耳机）上。

**场景 B：直播**

> 主播需要：游戏声 + 音乐进 OBS（采集卡虚拟设备），自己的监听耳机能听到全部，但不能有回声。她创建一个「直播模式」配置档：游戏与音乐 → 采集卡；监听 = 采集卡回环 → 耳机（B 路线，可选）。一键切换，下播后切回「日常模式」。

**场景 C：会议打断**

> 工作时间，音乐在音箱上放。Teams 来电。系统自动把 Teams 的「通信」角色路由到耳机，并把音箱上的音乐自动压低（ducking）——v1.1 提供，v1.0 先保证「Teams 固定进耳机」。

**场景 D：设备热插拔**

> 笔记本插上 USB 声卡，系统默认设备变了。RouteAudio 检测到新端点，按「设备别名/端口」规则把原先指向旧 USB 声卡的 3 个应用迁移到新声卡，并提示一次。

### 4.3 用户旅程

```
安装（无需管理员） → 首次向导（识别 2–3 个常用应用与 2 个设备）→ 拖拽建立首条路由
→ 提示「是否记住并在启动时自动应用」→ 最小化到托盘 → 日常无感
→ 换场景时：托盘/热键切配置档 → 出问题时：状态页看「未生效原因」+ 一键修复
```

## 6. 功能需求

> 优先级：**P0** = v1.0 必须；**P1** = v1.0 尽量 / v1.1 必须；**P2** = v1.x 之后。
> 每条需求的「验收标准」即为测试用例设计依据。

### 6.1 设备管理（FR-DEV）

| ID | 需求 | 说明 / 验收标准 | 优先级 |
| --- | --- | --- | --- |
| FR-DEV-01 | 枚举所有活动输出端点 | 列出 `DEVICE_STATE_ACTIVE` 的渲染端点；显示友好名、设备类型图标、采样率/位深、通道数、连接方式（内置/USB/HDMI/蓝牙/虚拟）。验收：插入 USB 声卡后 2 s 内出现在列表 | P0 |
| FR-DEV-02 | 区分三个设备角色 | 分别展示/设置 `Console` / `Multimedia` / `Communications` 默认端点；路由目标可指定角色 | P0 |
| FR-DEV-03 | 设备热插拔监听 | 注册 `IMMNotificationClient`，处理 `OnDeviceAdded/Removed/StateChanged/DefaultDeviceChanged/PropertyValueChanged`；UI 在 1 s 内更新 | P0 |
| FR-DEV-04 | 设备别名 | 用户可为端点设置别名（「游戏耳机」「客厅功放」），别名随端点 ID 持久化；设备重连后别名保留 | P1 |
| FR-DEV-05 | 识别虚拟设备 | 标记 VB-CABLE、VoiceMeeter、Steam Streaming 等虚拟端点，在 UI 中提示「虚拟设备：无实体输出」 | P1 |
| FR-DEV-06 | 测试音 | 对任一端点播放 1 s 粉红噪声/提示音，用于确认「这个设备到底是哪个」 | P1 |
| FR-DEV-07 | 端点能力探测 | 读取 mix format（采样率/位深/通道）、是否支持独占模式、当前是否被独占；用于延迟与格式决策 | P1 |
| FR-DEV-08 | 设备消失的兜底 | 目标端点被移除时，路由自动回退到该角色的默认端点，托盘通知一次，并在状态页标记「已回退」；设备回来后按策略恢复 | P0 |
| FR-DEV-09 | 默认设备管理 | 可设置系统三个角色的默认端点（与路由独立的功能），支持「一键把默认设备设为 X」 | P1 |
| FR-DEV-10 | 蓝牙设备处理 | 蓝牙端点断开重连后 ID 可能变化/复用；重连后按「设备指纹（名称+容器 ID）」重新匹配并恢复路由 | P1 |

### 6.2 应用与会话（FR-APP）

| ID | 需求 | 说明 / 验收标准 | 优先级 |
| --- | --- | --- | --- |
| FR-APP-01 | 枚举正在播放的应用 | 遍历所有渲染端点的 `IAudioSessionManager2` 会话，按进程聚合；显示进程名、图标、PID、当前电平、会话数 | P0 |
| FR-APP-02 | 枚举未发声但运行的应用 | 提供「所有运行中的程序」视图，可按可执行文件选择；避免「程序没出声就找不到」 | P0 |
| FR-APP-03 | 应用身份识别 | 以「可执行文件完整路径 + 文件版本信息（公司/产品名）+ 签名发布者」构成稳定 `AppIdentity`；避免仅按 exe 名匹配导致误伤（如多个 `chrome.exe`） | P0 |
| FR-APP-04 | 进程树聚合 | 浏览器/游戏启动器常有子进程出声；按「根进程 + 音频会话实际所属进程」双向索引；路由时对同一 AppIdentity 的所有相关进程生效 | P0 |
| FR-APP-05 | UWP / 商店应用 | 通过 `IAudioSessionControl2::GetSessionIdentifier` 与 AppUserModelID 识别打包应用（Spotify Store 版、Netflix 等） | P1 |
| FR-APP-06 | 应用分组 | 用户可把多个 exe 归入同一「应用组」（如 `Game.exe` + `Launcher.exe`），统一路由 | P1 |
| FR-APP-07 | 状态可视化 | 每应用显示：当前实际端点、期望端点、是否已生效、是否走了兜底（B 路线）、电平 | P0 |
| FR-APP-08 | 忽略列表 | 支持把系统声音、通知音、RouteAudio 自身排除在列表外 | P1 |
| FR-APP-09 | 退出后清理 | 进程退出后其会话与 UI 项在 3 s 内消失，但配置保留 | P0 |

### 6.3 路由（FR-RTE）

| ID | 需求 | 说明 / 验收标准 | 优先级 |
| --- | --- | --- | --- |
| FR-RTE-01 | 拖拽路由 | 把应用卡片拖到设备通道即完成路由；也支持右键菜单/键盘操作（可访问性） | P0 |
| FR-RTE-02 | 立即生效 | 策略路由应在 500 ms 内对**新建立的会话**生效；对正在播放的会话，若后端支持（重建会话/流式接管）应在 1 s 内切换 | P0 |
| FR-RTE-03 | 持久化 | 路由写入配置，程序重启、系统重启后仍在（由系统策略持久化 + 我们的配置双保险） | P0 |
| FR-RTE-04 | 生效方式可选 | 每个应用可选：`自动`（优先策略，失败则流式）/`仅策略`/`仅流式`/`虚拟声卡`，默认自动 | P0 |
| FR-RTE-05 | 批量应用 | 「全部恢复到系统默认」一键操作；支持对某设备通道「清空」 | P0 |
| FR-RTE-06 | 失败可解释 | 每个未生效的应用给出原因码（见 02 文档 §6.3 原因表）与修复建议；不允许静默失败 | P0 |
| FR-RTE-07 | 回滚 | 一次批量操作（配置档切换）失败时整体回滚到操作前状态 | P1 |
| FR-RTE-08 | 幂等 | 重复应用同一路由不产生副作用、不重复弹通知 | P0 |
| FR-RTE-09 | 多设备同播 | 同一应用可同时路由到 N 个设备（策略：主设备 + 镜像；镜像用流式复制），N ≤ 3 | P2 |
| FR-RTE-10 | 独占模式检测 | 检测目标端点是否被独占；若被独占，提示并（可选）按「独占优先」放弃路由 | P1 |

### 6.4 规则与配置档（FR-RUL / FR-PRF）

| ID | 需求 | 说明 / 验收标准 | 优先级 |
| --- | --- | --- | --- |
| FR-RUL-01 | 规则匹配条件 | 支持：进程名（通配符）、完整路径（通配符/前缀）、发布者签名、产品名、窗口标题（可选，默认关）、AppUserModelID、父进程、设备插入事件 | P1 |
| FR-RUL-02 | 条件组合 | 支持 `ALL`（与） / `ANY`（或）组合；单条规则内条件数 ≤ 10 | P1 |
| FR-RUL-03 | 规则优先级 | 数值优先级 + 显式顺序；冲突时高优先级胜出；同优先级按「更具体的匹配」胜出；结果可预览（「哪些应用命中此规则」） | P1 |
| FR-RUL-04 | 规则动作 | 动作集：路由到端点/角色、设置音量/增益、静音、加入配置档、启动/停止流式兜底 | P1 |
| FR-RUL-05 | 配置档 | 创建/重命名/复制/删除配置档；每档含路由表 + 音量 + 规则开关；当前档高亮 | P0 |
| FR-RUL-06 | 配置档切换 | 托盘菜单、全局热键（默认 `Ctrl+Alt+1..9`）、CLI、设备事件触发；切换 ≤ 1.5 s | P0 |
| FR-RUL-07 | 自动切换 | 触发条件：程序启动、设备插入、时间、前台窗口、手动；动作：切配置档 | P2 |
| FR-RUL-08 | 导入导出 | 配置为可读 JSON，支持导入/导出/粘贴；跨机器迁移时设备引用按「别名/指纹」重映射 | P1 |
| FR-RUL-09 | 规则测试器 | UI 中输入一个 exe 路径，显示命中哪些规则、最终结论 | P1 |

### 6.5 音量与混音（FR-VOL）

| ID | 需求 | 说明 / 验收标准 | 优先级 |
| --- | --- | --- | --- |
| FR-VOL-01 | 每应用音量 | 设置会话音量（0–100%），与系统音量混音器双向同步 | P0 |

### 7.1 性能与延迟

| ID | 指标 | 目标 | 测量方法 |
| --- | --- | --- | --- |
| NFR-PERF-01 | 策略路由额外延迟 | **0 ms**（不经过本程序） | 对比直连播放的环路延迟 |
| NFR-PERF-02 | 流式路由端到端延迟 | P50 ≤ 30 ms，P95 ≤ 50 ms | 1 kHz 脉冲串 → 采集/回放 → 互相关测时延 |
| NFR-PERF-03 | 不引入额外音质损失 | 策略路径：不经过本程序；流式路径：同采样率时直通不重采样，需重采样时由引擎完成，THD+N 劣化 ≤ 0.001% | 播放正弦 → 回环录制 → FFT |
| NFR-PERF-04 | 空闲 CPU | ≤ 0.3%（无流式）/ ≤ 2%（2 路 48 kHz 立体声） | 性能计数器 5 min 平均 |
| NFR-PERF-05 | 内存 | 空闲 ≤ 120 MB；每流式路 +15 MB | 任务管理器 / Working Set |
| NFR-PERF-06 | UI 响应 | 拖拽到生效反馈 ≤ 100 ms；主窗口打开 ≤ 400 ms | 手工 + 帧计时 |

| NFR-PERF-08 | 配置档切换 | ≤ 10 应用时 ≤ 1.5 s | 脚本计时 |

## 8. 约束与假设

| 编号 | 类型 | 内容 | 影响 |
| --- | --- | --- | --- |
| C-01 | 技术约束 | 策略路由依赖系统**未公开**接口（`Windows.Media.Internal.AudioPolicyConfig`），Windows 更新可能改变 IID/虚表 | 必须有版本探测、失败降级、快速修复通道（热更新配置或小版本） |
| C-02 | 技术约束 | 会话粒度为进程，无法区分同进程不同窗口 | 需求范围外 |
| C-03 | 技术约束 | 独占模式（WASAPI Exclusive）应用绕过音频引擎 | 策略无效，需虚拟声卡方案，v1 明确提示 |
| C-04 | 技术约束 | 受保护内容（DRM）路径不可采集 | 明确提示，不做绕过 |
| C-05 | 平台约束 | 进程回环需 Win10 2004+ | 更低版本只能用策略 + 虚拟声卡 |
| C-06 | 平台约束 | 虚拟声卡（VB-CABLE）为第三方、许可受限 | 不打包、不分发，仅检测与引导安装 |
| A-01 | 假设 | 目标用户为单用户桌面会话，非多用户服务器 | 多用户不保证 |
| A-02 | 假设 | 用户设备具备至少 2 个输出端点 | 单设备用户价值有限，向导提示 |
| A-03 | 假设 | 策略写入对同用户进程无需管理员权限（已由 EarTrumpet 实践验证） | PoC 复验 |
| A-04 | 假设 | 杀毒/EDR 不会因 `ActivateAudioInterfaceAsync` + VT_BLOB 参数告警 | 需在多款安全软件下验证 |

## 10. 验收标准

### 10.1 功能验收（UAT）

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| UAT-01 | 双设备分流 | 游戏与音乐同时播放，分别从耳机与音箱出声，无重复、无中断、无爆音；拔掉音箱 2 s 内游戏不中断、音乐回退并有提示 |

| UAT-04 | 异常可解释 | 人为让某游戏使用独占模式，UI 在 3 s 内给出「独占模式无法路由」原因与建议，不崩溃 |

- 72 h Soak 无崩溃、无泄漏、无爆音。
- 兼容矩阵（Win10 21H2 / Win11 22H2 / Win11 23H2 / Win11 24H2+，各 1 台实机或 VM）全部通过。
- 安装/卸载/升级/降级脚本通过；签名有效；无管理员权限安装通过。
