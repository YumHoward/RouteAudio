## 1. 结论摘要

| Gate | 假设 | 结果 | 影响 |
| --- | --- | --- | --- |
| **P1** | 策略 API 可写、可持久、免管理员、新会话生效 | ✅ **通过** | 主线成立，产品可行 |
| **P2** | 会话静音后进程回环仍能采到声音 | ❌ **不通过**（静音即静音） | B 路线不能用于「搬移」，降级为「镜像/录制」 |
| **C1** | 策略指向虚拟端点 + 设备回环采集可行 | ✅ **通过** | 「搬移」的兜底路径成立，但依赖虚拟声卡 |
| P3 | 流式延迟 P95 ≤ 50 ms | ⏳ 未测 | 需要渲染管线，下一步做 |

**一句话**：主路线（A 策略路由）完全可用；实时音频兜底（B）被证伪了「覆盖原声」这个前提；替代的 C 路线可用，但需要用户装虚拟声卡——这是一个产品取舍，需要决策。

## 2. P1：系统策略路由 —— 通过

**命令**：`AudioProbe.exe p1`

**实测记录**

```
[API ] IID = ab3d4648-e242-459f-b02f-541c70306324
[播放] pid=207120 当前端点: 扬声器 (Realtek(R) Audio)
[写入] role=eConsole    hr=0x00000000 target='{0.0.0.00000000}.{6a1e44c5-...}'
[回读] role=eConsole    persisted='{0.0.0.00000000}.{6a1e44c5-...}' OK
[写入] role=eMultimedia hr=0x00000000
[重启] pid=207068 端点: 扬声器 (网易虚拟音频设备)
[PASS] 策略在新会话创建时生效
[清理] persisted=''
```

**关键发现（必须写进实现）**

1. **IID 与虚表布局**：build 26300 上激活工厂只暴露两个 IID：`IUnknown` 与 `ab3d4648-e242-459f-b02f-541c70306324`（即 SoundSwitch 注释里的「H1H2/Win11」变体）。虚表槽位实测 `Set=25 / Get=26 / Clear=27`。
2. **设备 ID 必须是「设备接口路径」，不是端点 ID**（这是最初失败的根因）：
   - ❌ 传给 `SetPersistedDefaultAudioEndpoint` 的是 `{0.0.0.00000000}.{guid}` → 返回 `0x80070057 (E_INVALIDARG)`。
   - ✅ 正确格式：`\\?\SWD#MMDEVAPI#{0.0.0.00000000}.{guid}#{e6327cad-dcec-4949-ae8a-991e976a79d2}`（渲染端点的接口类 GUID）。
   - `Get` 返回的也是这个接口路径，需要解包后与端点 ID 比较（SoundSwitch 的 `GenerateDeviceId/UnpackDeviceId` 做的就是这个）。
3. **空字符串 = 清除覆盖**：`Set(pid, role, "")` 后 `Get` 返回空，回读验证通过。**不要调用 `ClearAllPersistedApplicationDefaultEndpoints`**——它会清掉系统里所有应用的覆盖（包括用户在 Windows 设置里的配置）。
4. **无需管理员权限**；跨进程写入有效；策略在**新会话创建时**生效（正在播放的会话不会立刻搬家）。
5. `E_INVALIDARG` 同时出现在「设备 ID 格式错误」与「进程当前没有音频会话」两种情况下——不能据此判断原因，需要先做格式转换、再按「会话是否存在」区分重试逻辑。

**持久化**：写入后重启目标进程仍然生效（音频直接出现在目标端点），说明策略保存在系统侧而非我们的进程内。跨系统重启的持久化尚未验证（需要重启机器，留到 M5）。

## 3. P2：会话静音 vs 进程回环 —— 不通过

**命令**：`AudioProbe.exe p2`

| 阶段 | RMS | Peak |
| --- | --- | --- |
| 静音前 | **-17.6 dBFS** | -14.6 dBFS |
| 静音中（会话静音） | **-96.7 dBFS** | -90.3 dBFS |
| 取消静音后 | -17.6 dBFS | -14.6 dBFS |

**解读**：进程回环的采集点在**会话音量/静音处理之后**。一旦把原会话静音（为了避免双声），采集端也只能拿到静音。因此「进程回环 + 静音原声」的搬移方案不成立。

**但 B 路线并未完全作废**：

- **镜像/同播**（原设备继续出声，同时复制到第二设备）不需要静音 → B 完全可用，且延迟可控。
- **录制某个进程**（不改变其输出）→ B 可用。
- **搬移**（原设备静音、只在新设备出声）→ B 不可用，需要 C。

证据 WAV：`artifacts/poc/p2-before-mute.wav` / `p2-during-mute.wav` / `p2-after-unmute.wav`。

## 4. C1：虚拟声卡桥接 —— 通过

**命令**：`AudioProbe.exe c1`（使用机器上已有的「网易虚拟音频设备」作为虚拟端点）

```
[初始] pid=208988 端点=扬声器 (Realtek(R) Audio)
[写入] 策略 → 扬声器 (网易虚拟音频设备)
[重启] pid=209332 端点=扬声器 (网易虚拟音频设备)     ← 策略生效
[窗口] c1-cable-capture: RMS -20.0 dBFS / Peak -17.0 dBFS / 2.52s
[双声检查] 测试音在物理端点上的会话数: 0             ← 无双重输出
[PASS] C 路线可行
```

**解读**：把应用由策略路由到虚拟端点（该端点没有物理输出 → 天然无声、不会双声），再对**虚拟端点做设备回环采集**，即可拿到该应用（或该「总线」上所有应用）的混音，随后渲染到任意物理设备。这条链路全部走公开 WASAPI API，稳定、可维护。

**代价**：需要用户安装一个虚拟音频设备（VB-CABLE / VoiceMeeter / 或未来的自有驱动）；多一层采样率转换；延迟增加 10–30 ms。

## 5. 架构调整建议

| 场景 | 采用 | 说明 |
| --- | --- | --- |
| 普通应用的「换端口」 | **A 策略路由** | 零延迟、零依赖，覆盖绝大多数场景 |
| 需要「同播到第二设备」 | **B 进程回环（仅镜像）** | 不改原输出，只复制一路到目标端点 |
| A 失效且必须「搬移」 | **C 虚拟声卡桥接** | 需要虚拟端点；策略把应用推进去，再采集转发 |
| 独占模式 / DRM | 明确提示 | 策略无效、采集也拿不到，任何用户态方案都无解 |
| 低延迟 / 多路混音 | D 自有驱动（v2 评估） | 签名与开发成本高 |

对应文档修改：`02-技术方案与架构设计.md` §3.1 / §3.2 / §3.5 / §6.4，`04` §A、§B.3。

## 7. 复现步骤

```powershell
# 构建
dotnet build src/RouteAudio.sln -c Debug

# 设备与会话
tools/AudioProbe/bin/Debug/net8.0-windows/AudioProbe.exe devices
tools/AudioProbe/bin/Debug/net8.0-windows/AudioProbe.exe sessions

# P1：策略路由端到端（会自动起停测试音子进程）
AudioProbe.exe p1

# P2：静音对进程回环的影响（会写 WAV 到 artifacts/poc）
AudioProbe.exe p2

# C1：虚拟声卡桥接（使用机器上第一个虚拟端点）
AudioProbe.exe c1
```

> 注意：`p1` / `c1` 会修改系统的「按应用默认端点」策略，运行结束后会尝试清除；若异常中断，可在 Windows 设置 → 系统 → 声音 → 音量合成器 中手动恢复。
